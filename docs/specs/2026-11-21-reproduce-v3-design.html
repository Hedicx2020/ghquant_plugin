现存问题

问题 1　token 主要花在主会话和重复读文书上

一次复现里最贵的不是某个子 agent，而是编排它们的主会话。

主会话贵在三件事：

  • 每派发一次子 agent，它前后要走十余轮：读执行卡、手写派发提示词、逐个文件点收、原样粘贴门禁输出、写状态。
  • 它还亲自誊写外审意见、对读规格书和盲提取结果、整读 30–49KB 的 state.json。
  • r009 的主会话因此压缩了 6 次，另有 31 次轮询超时、34 次续派。

每次派发都有一笔起步成本。r009 里任何一个子 agent 开工前都要全量读四份文书，合计约 9 万 token：规格书 3.8 万、假设登记簿 3.6 万、覆盖矩阵 1.1 万、计划 0.8 万。整场运行规格书被读了 43 次，假设登记簿 38 次。coder 和 verifier 干完还要回写这些大表，要改就得先读全文，这部分文件合计 104KB 和 233KB。

账单是「轮数 × 上下文」。r007 的 planner 一次派发就有 87 次模型调用，累计输入 1022 万 token。每一轮都把同样的上下文再带一遍，所以起步成本降下来，整场都跟着降。

按计价权重折算（缓存读 0.1、未缓存输入 1、输出 5），r007 全案的开支里缓存读占 62%、未缓存输入占 28%、输出占 10%。所以主轴是减少轮数和每轮携带的上下文，压缩输出的收益最小。

问题 2　人工闸门只是提示词里的约定

「暂停等人」现在靠主会话自觉。三个案例的状态文件里留着这样的记录：

案例事件记录内容

r007verify_circuit_breaker_override_authorized"authorization":"user_auto_authorized"

r006human_override 两条放行第 3 次、第 4 次修复

后两条是否真有人批准，无从查证，因为放行记录都是主会话自己写的。根源在于「人答复后解除暂停」和「自行解除暂停」用的是同一条命令，代码分不出来。「同一门禁连续 3 次失败就熔断」也只写在文字里，没有任何计数。

问题 3　过程看不见

  • 返工不入账。r010 按合同约 22 次派发，实际 34 次。多出来的修复、复审、降级重规划在状态文件里没有任何痕迹。
  • 停滞没人知道。一个案例在 plan 阶段停了 136 小时，r007 累计空闲 119 小时，都是事后才发现。
  • 外审悄悄降级。r010 的规格外审和代码外审各超时两次，都退成了同宿主替身，评级因此封顶 B。超时的原因见问题 4。
  • 返工是常态。r009 的 10 个阶段只有 5 个一次过门禁，r010 是 11 个里 8 个，r008 是 11 个里 9 个，但没有地方能一眼看到卡在哪。

问题 4　外审又慢又贵，结果外审反复被打回

外审脚本调 Codex 时不指定模型和推理强度，输入只给文件路径。r010 的三处外审在 Codex 侧留下了 26 个会话，这些用量今天不在任何账本里。

超时的根因有四个，时限只是最后一环：

  • 推理强度没人管。脚本不指定，跟着当时的全局配置走，r010 用的是 ultra。
  • 审查方自己再分子代理。每次外审都派出 2–3 个子代理，再等它们回来。
  • 输入靠一段段读。约 360 次 sed、nl、rg 命令。每读一段就多一轮，每轮都带着已读的全部内容。
  • 复审等于重审。r010 结果外审的第二轮用的仍是完整提示词，工作量与首轮相当。

结果外审为什么总要两三轮？三个案例的 8 条 critical 意见，全是文书与机器产物对不上：

类型条数例子
手抄的数值不符，或是旧轮残留4r008 的验证报告把 5.09% 抄成 5.28%；r009 修完后正文仍写「共 84 项」，实际已是 86 项
计数对不上2r010 声称刷新了 22 个缓存，目录里只有 21 个

其中两条出在第二轮，是修复时自己留下的旧数。这类问题机器在外审之前都能查出来。归因缺量级分解、假设方向与实测相反这类实质性意见都是 major，仍然要靠外审。

问题 5　数据缺不缺，没有机器把关

plan 里每条数据需求只有三个自由文本字段，没有任何门禁去核对它。下面是 r010 的原样：

data_requirements:
  - name: A股个股前复权日行情（形态识别主数据）
    source: ashare_stock_price_forward.parquet
    status: available

planner 判断数据可得性的唯一依据是一份手写的数据目录。目录写错，plan 就跟着错。

r010 的经过是这样的：目录写着有，plan 标了 available，规格外审也过了。到第一个 milestone 编码实测，才发现 2014–2024 几乎没有数据，H 股平行回测和持仓清单只能判不可复现。

另一类缺口是目录里写明没有的数据，比如 r010 的分析师一致预期。planner 判出来了，流程也暂停了，但处置环节没有硬闸门，结果就是问题 2 里的自行降级。

数据层本身也被绕开。r009 的代码里有 63 处直接 read_parquet、5 处 JyPy 或直连 SQL，公共的 data_loader 只覆盖个股行情与状态过滤。想临时换一份数据，没有统一的入口。

问题 6　两个宿主已经漂移，旧案例要接得上

  • Codex 侧的 coder、planner 角色文件落后于正本，经济档在 Codex 上不生效。
  • r007 的 28 个子代理里，有 12 个是带着主会话历史分叉出去的，起步就背着主会话的上下文。
  • r010 实际跑在没有适配文档的第三个宿主上。
  • 12 个案例里有 9 个没有收尾：4 个等评审，4 个阻断，1 个在跑。改造不能让它们卡死。
  • 8 月写的《图工程优化方案》13 项一条都没落地，这次一并吸收。

改动方案

总的思路：把「流程怎么走」从写给主会话看的文字，搬进确定性的 Python 内核。Claude Code、Codex 和主会话都只是内核外面的一层薄壳。12 个阶段、现有门禁的判定、8 个角色的分工、异构外审都不变。

改动 1　内核接管编排

主会话以后每次派发做什么

  1. 运行 flow next，拿到工单：派哪个角色、任务文件在哪、该交回什么。
  2. 把一句话交给子 agent：读任务文件并严格执行，只回一行 DONE 或 BLOCKED。
  3. 运行 flow done。内核点收产物、合并回执、过门禁、记事件、刷看板。通过只打印一行，没过才展开明细。

外审怎么改

  • 外审改为后台执行并放宽超时，flow wait 轮询结果，不再卡在 600 秒。
  • 多轮外审的汇总由内核从各轮原件生成，意见逐条自动登记，不再由主会话手写。
  • 超时先按原输入延长时限重试一次，仍超时才降级。

仍然不交给代码的判断

判断归谁
每条外审意见是接受、拒绝还是搁置，派谁去修主会话。只给它意见摘要；critical 不得拒绝或搁置
并行编码造成的假失败怎么分诊主会话。内核校验当时确有并行编码，每个 milestone 限一次
可行性阻断、阻断级歧义、数据缺口、熔断之后怎么办你

内核会不会把案例卡死

内核分两层。工具层是一组可以单独调用的命令：切任务文件、合并回执、跑门禁、外审、数据体检、预检。调度层只是一张声明式的步骤表，决定下一步派谁。

  • 每项能力先做成工具层命令，旧执行卡也能用，之后才由调度层接管对应阶段。
  • 任何阶段都可以按案例退回「执行卡驱动 + 工具层」，要写原因并留痕。步骤表判断不了的情况不会把案例卡死。
  • 闸门和等待态的守卫在状态层，退回执行卡也绕不过去。

动哪些文件：新增 tools/flow.py 与 tools/flowlib/；tools/state.py 加案例锁和状态流转守卫；tools/check_gates.py 只抽函数；SKILL.md 从 28.7KB 压到 5–6KB；13 张执行卡逐批退役。

改动 2　任务文件切片与回执

起步成本有读、写两半，两半都要去掉。

读：任务文件只装这一步要用的

  • 内核按「角色 × 步骤」从原始文书逐字切片。coder 拿到的是本 milestone 的要素全文、它直接依赖的数据要素、相关假设的精简卡、矩阵里属于它的行；其余要素和假设各留一行索引。
  • 不够用时，子 agent 用 flow get 按编号取单个要素或假设。每次取用都记账，用来校准配方。
  • 切片必须是原文的逐字子串。原文一改，对应的任务文件自动失效。

写：回执代替回写

  • coder、verifier 不再直接改覆盖矩阵和假设登记簿，而是把要回填的内容写进回执。
  • flow done 校验「改的是本步的行、状态流转合法」之后在锁内合并，新假设的编号由内核发。
  • 多个 milestone 的 verifier 因此可以并行，不再排队。

不再手抄的东西。验证报告和最终报告里的对比总表、达标计数、产物清单，由内核从对比表和结果目录生成后嵌入，正文只引用指标编号。三个案例里这两份文书各有 94–278 行手抄表格，结果外审的 critical 多数出在这里。

不切的通道。提取、规格审计、三处外审与第二意见照旧全量；实现审计和 verifier 对代码的全量读不动；实现审计仍拿到全部假设。这些冗余是防偷懒用的，8 月的方案已经论证过不能裁。

动哪些文件：新增 tools/flowlib/mdslice.py、packs.py；8 个 agents/quant-*.md 的输入合同改成「按任务文件执行、不够再取、交回执」。

现在改后

每个检查点你有四种决定：通过、修改后继续、回退到某一步、终止。选「修改后继续」时，你直接改文件或口述，内核按内容哈希标出哪些步骤过期，只重跑受影响的部分。假设登记簿的 Excel 批量修订从 plan 定稿之后就能用，不必等到报告出来。

禁读护栏

盲审通道的原文、运行缓存、扰动产物、大体积数据文件，不该读的角色读不到。Claude Code 上用读文件前的钩子按角色拦截。Codex 没有对应的拦截点，改为事后从会话记录核对，命中的在看板标出。

改动 4　外审引擎与结果预检 对照评估后新增

现在改后
输入只给路径，审查方分段读内核预先拼好输入包随提示词送入：所需文件带行号的全文、数值字面量在代码里的命中清单。审查方仍有整个目录的只读权限
推理强度跟着全局配置走命令里显式指定：首轮 high，复审 medium，可按审查点调整
审查方自己再分子代理调用时关闭多代理，事后从会话记录核对
复审等于重审第二轮起只给差量包：上一轮的意见与回应、改动处的差异。只核对意见是否闭环、改动有没有引入新问题
600 秒超时即作废，再原样重试后台执行，时限放宽到 30 分钟。超时后降一档推理强度重试一次，仍超时才降级。不缩减输入
盲提取的两个阶段写在同一份提示词里，靠审查方自觉拆成两次调用：第一次只给原文，第二次才给规格书。事后可以核对第一次没有读过规格书
外审的用量不在任何账本里token、耗时、读文件次数记入事件流和看板

结果一致性预检

结果外审和写报告之前，机器先核四件事，不过就不派外审：

  1. 登记为核心的结果要素，在对比表里都有条目，或显式标为不适用。
  2. 对比表里的数值与原始指标文件在舍入范围内一致。
  3. 原始产物里算不出的指标，没有被计为通过。
  4. 文书里的计数和指标值与机器结果一致。对比表每次变动后，扫描文书里残留的旧数值，给出清单。

预检只查机械性的一致，不生成审计意见。按问题 4 里那 8 条 critical 的类型回看，这四项都能提前拦下，三个案例有望各少一轮外审和一次修复派发。

动哪些文件：tools/external_review.py 加推理强度、多代理开关和输出落盘；新增 tools/flowlib/extreview.py、precheck.py；外审提示词新增两次调用和差量复审两种模板。

改动 5　数据体检与缺口处置 按审批意见新增

原则有三条：数据缺不缺由机器查；缺了怎么办由你定；用 mock 跑出来的数字进不了结论。

三道机器检查

检查什么时候查什么
目录体检安装时，以及每次新建案例时数据根下每个文件的字段、行数、日期起止；带证券代码和日期的表再算每年的标的数和交易日数。只读元数据，秒级完成。结果生成一张「数据实况表」交给 planner，手写目录降为说明性文字
需求体检plan 写完之后，外审和编码之前逐条核对 plan 的数据需求：文件在不在、字段齐不齐、区间盖不盖得住（含预热窗口）、每年标的数有没有塌陷、频率、主键重复、关键字段缺失率、财务数据有没有披露日列
运行期复核verify 时这次运行实际读了哪些文件、各自是真实还是 mock；数据在体检之后有没有变过

为了让机器查得动，plan 的每条数据需求多几个可选字段。旧 plan 没有这些字段，只做文件存在性检查。

data_requirements:

    source: hkshare_stock_quote.parquet
    status: available
    files: [hkshare_stock_quote.parquet]     # 以下为新增的可选字段
    fields: [stock_code, date, close]

缩小范围只在有数据的区间或标的上复现登记假设，继续
先用 mock 试跑用模拟数据先把代码和流水线跑通。这一轮只算试跑，不出结论见下面的规矩
砍掉相关要素标为不可复现，其余照做继续
终止放弃这份研报案例结束

无人值守时的默认做法可以在启动时声明：--on-missing ask|mock|stop。默认是 ask，停下来等你。

mock 的规矩

定位选了 mock，这个案例整轮只算试跑。编码、内审、代码外审照常做：它们不依赖数据取值，真实数据到位后只要代码没变就仍然有效
怎么生成按来源优先级取：你给的样例文件；借一张结构相近的真实表改键、改日期，保留真实的截面分布和缺失形态；都没有才按字段类别随机生成。纯随机数据容易算出除零、奇异矩阵或空信号，所以排在最后。生成规格先在检查点给你看
怎么接入公共数据层新增统一的取数入口 data_path()，先查本案例的覆盖目录，再查数据根。代码不用为 mock 写分支，换回真实数据时也不用改代码
怎么隔离试跑的结果写到单独的目录，真实结果目录里只会有真实数据算出来的东西。每次运行留一份数据清单，写明每个文件是真实还是 mock。门禁核对真实结果的清单里没有 mock 文件
停在哪验证只查三件事：跑得通、产物齐、指标都算得出。然后停在「试跑完成」，不迭代、不出 verdict、不写报告
之后怎么走等真实数据：到位后重检，结构和 mock 规格一致只重跑验证，不一致则相关 milestone 的编码标为过期。也可以改用别的处置按真实数据走完，或终止
不做什么不做逐指标的隔离，不做真假数据混跑。缺的是非核心数据而又想先拿到主体结论，就选「砍掉相关要素」或「缩小范围」，数据到了再补回

动哪些文件：新增 tools/flowlib/datacheck.py、tools/mockdata.py；common/data_loader.py 加 data_path() 与数据清单；templates/_plan_template.md、agents/quant-planner.md 加可选字段；tools/check_gates.py 新增三条数据类检查（plan 两条、verify 一条），只对新建案例生效，现有检查不动。

改动 6　看板、事件流与计量

  • 每一步的开始、结束、门禁结论、返工、检查点都追加进 events.jsonl。返工派发从此有账可查。
  • 每次 flow done 之后重新生成一个静态页面 board.html：当前停在哪、等谁、停了多久；阶段 × milestone 的进度；待你决定的检查点；门禁明细；用量；返工清单。不起服务，双击就能开。另有一个全案例总览页。
  • 在途步骤超过 3 小时没有新事件就告警并开检查点。token 和时长预算超限同样开检查点。
  • 用量分三档记账：任务文件字节数和耗时，总是有；宿主回报的 token 数，Claude Code 有；宿主会话记录里的精确值，读得到就用。未缓存输入、缓存读写、输出分开记。
  • 外审的用量和每次运行的耗时也记进来。r010 的外审在 Codex 侧用掉 4619 万 token，今天哪里都查不到。
  • state.json 只留最近 50 条事件，体积从 30–49KB 降到几 KB。

改动 7　两个宿主与旧案例

  • 工单协议与宿主无关。每个宿主一张适配卡，只回答四件事：怎么把工单变成一次派发、怎么后台执行与等待、怎么向人提问、会话记录在哪。提供 Claude Code、Codex 和一张通用卡。
  • Codex 侧重新同步角色文件并加一致性测试；派发一律不继承主会话历史；经济档补齐。
  • 9 个未收尾的旧案例：当前阶段按原执行卡跑完，下一阶段起进入内核。状态文件首次写入时自动迁移并留备份，旧执行卡保留到这些案例全部离开。

实施顺序

按风险从低到高分六批，每批做完停下来给你验收，再做下一批。每项能力先做成可以单独调用的命令，旧执行卡也能用，再由内核接管对应阶段。

怎么证明省了

r010 跑在第三个宿主上，没有留下任何用量记录，所以 token 对照改用 r009：把它复制成新编号、回退到编码起点，只重跑 m1、m2 两个 milestone，和原记录逐次派发对比。

  • 目标：coder 任务文件不超过现行全量的四成；主会话每次派发不超过 4 次内核调用；同一段流程的累计输入和未缓存输入各降四成以上。
  • 保真指标不得下降：内审和外审的发现数与严重度、门禁首过率、已对上的指标数。
  • 起点是从终态文书回退出来的，带着首跑的后见之明。派发次数的对比会偏乐观，主要看单次派发的上下文和轮数。
  • 外审另做一次重放：用新引擎重跑 r010 的代码外审，看能否在时限内给出结论，并对比原来两次尝试的 2573 万累计输入。这一项要花少量 Codex 额度。
