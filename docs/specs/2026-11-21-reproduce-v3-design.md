# 研报复现插件 v3 改造方案

## 一、背景

插件 `quant-report-reproduce` 当前为 v2.12.0（Claude Code + Codex 双宿主，12 阶段门禁状态机 + 8 个量化角色 + 异构外审）。r001–r010 跑下来，提出四个改进方向，且必须保持双宿主可用：

1. 减少 token 开支
2. 架构优化：多种数据源（本地文件 / API / 数据库 / MCP）、多篇引用、与知识库结合保存复现结果
3. 复现过程更可视化、可控，方便随时打断校验
4. 允许本体接入（量化助手项目 `~/quant_assistant`，即「量研桌面」）

已确认的取舍（2026-11-21）：

- 流程控制从 SKILL.md / 执行卡的文字迁到**代码驱动内核**。
- 本体只有作者自用，其他客户安装后不一定接入，所以本体做成**可选适配，默认关闭**，内核不依赖它。
- 知识库落点由本方案给建议（见 7.2）。
- **本轮只实施第一、二期**（第四、五、六节）；第三至五期只给纲要并预留扩展点（第七节）。
- 一处调整：原定用 r010 同 PDF 重跑来对比 token，核对后发现 r010 跑在 ZCode 上，没有留下任何用量记录，只能比结论。token 对照改用唯一有逐次派发用量记录的 r009（见第十节第 5 项）。
- 追加要求（审批反馈）：加一层数据体检。复现要用的数据缺不缺先由机器查清；缺了由人选处置方式，其中一种是先用 mock 数据试跑（见 4.5）。
- 对照评审后的调整：Gemini 评过一轮，逐条核对事实后采纳四处、收窄一处。采纳：外审从根因上治理（4.11）、结果外审前加一致性预检（4.6）、机器禁读护栏（4.6）、内核明确分成工具层与调度层且阶段可以退回执行卡驱动（第三节）。收窄：mock 改为整轮试跑，不做逐指标隔离（4.5）。代码驱动内核的路线不变；没有采纳单列一批公共引擎提速，理由见第十一节。

## 二、实测证据

来源：`.specstory/history/` 里 r008、r009 的完整会话记录，Codex 会话记录里的 r007，各案例 `state.json` 与文书字节数，三路代码勘查和两路设计评审。

**r009（hard，5 个 milestone）一次复现的子 agent 开销：39 次派发，15.0 小时，1794 次工具调用**

| 角色 | 派发次数 | 峰值上下文合计 | 占比 | 备注 |
|---|---|---|---|---|
| coder | 13 | 287 万 | 41% | m2 派了 4 次、m3 派了 3 次 |
| verifier | 8 | 133 万 | 19% | 两次 revise 重跑各 198 / 281 次工具调用 |
| auditor（逐 milestone 实现审计） | 8 | 118 万 | 17% | |
| planner | 6 | 84 万 | 12% | 同一 agent 被续派 5 次，上下文单调增长 |
| extractor、auditor(spec)、auditor(result) | 4 | 77 万 | 11% | |
| 合计 | 39 | 699 万 | | 单次派发峰值上下文：最小 9.0 万，中位 17.1 万，最大 40.2 万 |

结论：

1. **每次派发的上下文地板约 9 万 token，等于全量读四份文书**：r009 的 `spec.md` 3.8 万、`assumptions.md` 3.6 万、`coverage_matrix.md` 1.1 万、`plan.md` 0.8 万。整场运行里 `spec.md` 被读 43 次、`assumptions.md` 38 次。
2. **地板有读、写两半**：coder、verifier 还要回写矩阵、假设登记簿、`verify_report.md`，要改就得先全读。r009 里这些回写文件合计 104KB（coder）和 233KB（verifier），比按 milestone 切出来的输入还大。
3. **真正的账单是「轮数 × 上下文」**：Codex 宿主的 r007 有逐轮记录，28 个子代理累计输入 1.87 亿 token，光 planner 一次派发就有 87 次模型调用、累计 1022 万。r009 没有逐轮记录，按工具调用数乘平均上下文估算在 2–3 亿。累计输入里约 95% 是缓存命中，单价低但照样计费、计额度，所以后面的计量把未缓存输入、缓存读写、输出分开记。按缓存读 0.1、未缓存输入 1、输出 5 的权重折算，r007 全案开支里缓存读占 62%、未缓存输入占 28%、输出占 10%，主会话的输出只占它自己开支的 5%。所以主轴是减少轮数和每轮携带的上下文，压缩输出的收益最小。
4. **主会话是最大的单一消耗者**：r007 主会话累计输入 2.13 亿，占全案 53%。它的 28 个子代理里有 12 个是带着主会话历史分叉出去的（记录里计数器从父会话的累计值起步）。r009 主会话压缩 6 次，每次派发前后走十余轮（读执行卡、手写派发提示词、`ls` 点收、原样粘贴门禁输出、写状态），另有 31 次轮询超时、34 次续派；它还亲自誊写外审意见、对读 spec 与盲提取结果、三次整读 31–49KB 的 `state.json`。
5. **返工派发看不见**：r010 按合同约 22 次派发，实际 34 次（coderfix、reaudit、plan-degrade 等），state 事件里没有任何记录。
6. **人工闸门只是提示词约定**：r010 进入 `paused_blocked` 6 分钟后出现 `degrade_decision {"by":"orchestrator_autonomous","user_confirmed":false}` 并继续，明写着没有人确认。r006 的两条 `human_override`（放行第 3、第 4 次修复）和 r007 的 `verify_circuit_breaker_override_authorized`（`"authorization":"user_auto_authorized"`）都是编排会话自己写的事件，是否真有人批准无从查证。「同一 gate 连续 3 次 FAIL 熔断」没有任何代码计数。
7. **外审又慢又贵，超时的根因不在时限**：`tools/external_review.py` 调 Codex 时不指定模型、推理强度和任何开关，输入只给文件路径。r010 的三处外审在 Codex 侧留下 26 个会话、累计输入 4619 万 token：每次都以 ultra 推理强度运行（跟着当时的全局配置走），并自己再分出 2–3 个子代理（26 个会话里 19 个是子代理），靠约 360 次 `sed` / `nl` / `rg` 一段段读文件。spec、code 两处各超时两次，3157 万累计输入没有留下一条意见，随后降级为同宿主替身，评级封顶 B。复审轮用的仍是完整提示词，第二轮的工作量与首轮相当。多轮外审没有规范文件，r010 结果外审的「三轮汇总视图」是主会话手写的。这些用量今天不在任何账本里。
8. **结果外审的 critical 全是文书与机器产物对不上**：r008、r009、r010 的结果外审共提出 8 条 critical，全部是机械性不一致：文书里手抄的数值与 `comparison.json` 不符或是旧轮残留（4 条）、计数对不上（2 条）、核心要素在对比表里缺条目（1 条）、占位值被计为通过（1 条）。其中两条出在第二轮，是修复时自己留下的旧数。每多一轮就是一次重审加一次修复派发，而这类问题机器在外审前都能查出来。归因缺量级分解、假设方向与实测相反这类实质性意见都是 major，机器查不了，仍要靠外审。
9. **数据缺不缺没有机器把关**：plan 里的数据需求只有名称、来源、状态三个自由文本字段，没有任何门禁核对。`templates/data_catalog.md` 是手写的，把港股个股行情写成「2000-10 至今」；实测这个文件 2014–2024 每年只有 1–9 只股票有数据，2025 年起才有 2500 多只。r010 的 plan 照目录标了 available，缺口到 m1 编码时才被发现，而机器查它只要 0.2 秒（全目录 118 个文件 29GB 只读元数据的体检用 0.1 秒）。目录里写明没有的数据（分析师一致预期）planner 倒是判出来了，但处置环节没有硬闸门，被主会话自行降级。数据层本身也被绕开：`src/r009_*` 有 63 处直接 `read_parquet`、5 处 JyPy 或直连 SQL，`common/data_loader.py` 只覆盖个股行情与状态过滤。
10. **引用缺口无处登记**：一个案例只能输入一个 PDF；r010 依赖的前篇报告不在 PDF 里，只能判 blocking，然后被自行降级为自定参数。
11. **8 月的《图工程优化方案》完全没有落地**（`docs/specs/2026-08-11-graph-optimization-proposal.md`，A1–A5 / B1–B8 共 13 项）。本方案吸收其结论与「刻意冗余不裁」清单。
12. **双宿主已出现漂移**：`.codex/agents/quant-{coder,planner}.toml` 落后于 md；economy 在 Codex 上不生效；r010 实际跑在没有文档的第三宿主 ZCode 上，其派发方式正是「任务写进文件，派发消息只说读文件」。

## 三、总体架构：一个内核，四个适配面

```
        外壳（宿主适配，薄）  Claude Code 技能 | Codex 技能 | 通用宿主 | 量研桌面（第五期）
                                      │  工单协议：flow next / flow done
┌─────────────────────────────────────▼────────────────────────────────────┐
│ 内核（宿主无关、确定性 Python，位于 tools/）                                │
│ flow 步骤调度 · 上下文包 · check_gates 门禁（判定不改） · state 状态         │
│ events.jsonl 事件流 · 看板 · 检查点 · 计量 · 数据体检                       │
└──────────┬──────────────────────┬───────────────────────┬─────────────────┘
     数据适配（第三期）        知识适配（第四期）        本体适配（第五期，可选）
  parquet / 文件 / SQL /    本地案例库 / Markdown 库 /   量研桌面本体：
  API / MCP → 案例快照       quant_wiki                  读语义、写候选事实
```

工单是内核发给主会话的一条指令：派哪个角色、让它读哪个任务文件、该交回哪些文件。主会话不再自己读执行卡、拼提示词。

内核分两层。工具层是一组可以单独调用的命令：切任务文件、合并回执、跑门禁并记账、外审、数据体检、一致性预检、看板。调度层是 `flow next` 背后的一张声明式步骤表，只决定下一步派谁，是工具层之上的薄封装。每项能力先以工具层命令交付，旧执行卡也能调用，随后才由调度层接管对应阶段。任何阶段都可以按案例退回「执行卡驱动 + 工具层」（`flow pin`，要写原因并入事件流），步骤表判断不了的情况不至于把案例卡死。闸门与等待态的守卫在状态层，退回执行卡也绕不过去。

不变的东西：12 个阶段及其现有门禁检查项的判定语义（本轮只新增数据类与一致性类检查项）、`templates/standards.json` 达标口径、8 个角色的职责划分、异构外审三审查点与盲提取、机器解析的文书格式（spec 要素标题块、矩阵表、plan frontmatter、audit_responses 表、分页标记）。原始文书始终是权威来源，切片与摘要都是只读派生物；内核永不写 `src/<id>/` 与 `output/<id>/results/`。

## 四、本轮 · 第一期：内核 + 上下文包 + 数据体检 + 外审 + 计量

### 4.1 内核命令

新增 `tools/flow.py`（只依赖标准库与 pyyaml，因为用户目录里已有的 pyproject 不会被更新）。它在进程内调用 `state.py`、`check_gates.py`、`external_review.py` 的函数，不另起判定口径。

| 类别 | 命令 | 作用 |
|---|---|---|
| 推进 | `flow init <pdf> [--slug --mode --policy --until]` | 编号、骨架、PDF 转文本、PDF 哈希撞库检查、过 G-IN，零派发 |
| | `flow next <id>` | 返回 `{orders, wait, halt}`：可派发的工单、在途步骤、停在哪个检查点。确定性步骤（填外审模板、切盲提取块、从 plan 播种 milestone、统计覆盖率、渲染结果页、导出假设表）由内核就地连跑，不出工单。重复调用结果不变 |
| | `flow done <id> <step…>` | 一把锁内完成：点收产物 → 校验并合并回执 → 提交状态 → 步骤收口处跑门禁 → 追加事件 → 采集用量 → 刷新看板。通过只打一行，未过才展开明细并附对应的处理说明 |
| | `flow fail <id> <step> --class incomplete\|blocked\|crashed` | 记失败；按重派上限给续派单或开检查点 |
| | `flow adhoc <id> --role --reason --instruction <文件> --writes <路径>` | 步骤表之外的临时派发，有限额并入账；没有它，内核照样会被表外派发绕开 |
| 外审 | `flow exec <id> <step> --detach`、`flow wait <id>` | 外审在后台跑，`wait` 轮询结果。输入包、推理强度、差量复审与超时处理见 4.11 |
| 人工 | `flow decide <id> <检查点> --choice --quote`、`flow revise`、`flow accept`、`flow reopen` | 检查点放行、定向重跑、收尾、回退重开 |
| 取块 | `flow get <id> element F12 \| assumption AS7 \| matrix-row F12 --step <step>` | 子 agent 的逃生门，每次调用记事件 |
| 数据 | `flow data probe`、`flow data check <id>`、`flow data recheck <id>` | 体检数据目录；核对本案例的数据需求；数据补齐后重检（见 4.5） |
| 工具层 | `flow pack <id> <step>`、`flow merge <id> <step>`、`flow gate <id> <阶段>`、`flow review <id> <审查点>`、`flow precheck <id> --stage result\|report` | 调度层用的就是这几条，也可以单独调用：切任务文件、合并回执、跑门禁并记账、发起外审、结果一致性预检。仍由旧执行卡驱动的阶段靠它们拿到同样的收益 |
| 只读 | `flow status [id]`、`flow explain <step\|gate>`、`flow cost <id>` | 进度与全案例总览、按需取异常处理说明、用量汇总 |
| 维护 | `flow migrate [id]`、`flow fork <id> <新编号> --from <阶段>`、`flow pin <id> <阶段> --mode card\|kernel --reason` | 旧案例迁移；把一个案例复制成新编号并回退到指定阶段的起点（对照回归用）；把某个阶段退回执行卡驱动或交还内核 |

一张派发工单包含 `step_id`（如 `implement.m2.code#1`）、`kind`、`role`、`model_tier`、`prompt_file`、`prompt_inline`、`outputs`、`writes`、`receipt`、`parallel_group`。主会话只做一件事：把 `prompt_inline`（「读取任务文件并严格执行，最终只回一行 DONE 或 BLOCKED」）交给对应角色。任务文件与回执落在 `workspace/<id>/flow/{tasks,receipts}/`，全程可追溯。

### 4.2 原由主会话亲自做的事，各归何处

| 现在的做法 | 改造后 |
|---|---|
| 读执行卡、手写派发提示词、`ls` 点收、粘贴门禁输出、写状态 | 内核（步骤表 + 任务文件 + `done`） |
| 手填 4 份外审 prompt、备料（common 签名、R 类数值字面量） | 内核渲染；填充后仍有占位符残留即判失败 |
| 外审台账读改写、把意见誊写进 `audit_responses.md`、多轮意见手工汇总 | 内核：各轮原件只由 `external_review.py` 写，内核取并集生成规范文件，「复核」列按末轮是否仍列出该意见填写 |
| 对读 spec 与盲提取结果写 `extract_diff` | 内核把外审第二阶段结论与内审意见投影成 DIF 行（抽查 5 个案例，「依据」列都指向这两处） |
| verify 三分支、iterate 轮次与三出口、oos 触发、覆盖率统计、外审降级链、难度裁剪 | 内核查表 |
| 每条外审意见的处置（接受 / 拒绝 / 搁置）与派谁修 | **仍归主会话**，以判断工单形式、只喂意见摘要；critical 不得拒绝或搁置；「回应」列由修复回执回填。被审方与内审方都不宜自裁 |
| 流水线干扰造成的假 FAIL 分诊 | 仍归主会话，但内核校验「验证期间确有别的 milestone 在编码」，每个 milestone 限一次 |
| blocked 处置、阻断级歧义、可行性降级 | 人（检查点） |
| 案例英文短名、对用户的人话转述 | 主会话 |

### 4.3 闸门与熔断代码化

- 等待态（`paused_blocked`、`awaiting_review`）下 `flow next` 只返回 `halt`，门禁转绿也不会自动放行。不新增状态值：中途检查点的等待沿用 `awaiting_review`，阻断沿用 `paused_blocked`，具体停在哪个检查点记在 `state.checkpoints`，`flow status` 与看板据此区分中途检查点与最终评审。`/goal` 的「到达终态即停」文案不用改。
- `state.py` 给 `set status` 加流转守卫，并拒绝保留事件名。今天「人答复后解除暂停」的合法做法与 r010 的绕过是同一条命令，所以封禁必须和合法出口（`flow decide`、`flow revise`、`flow accept`）同批上线，否则旧案例全部卡死。
- 检查点分两类。可按策略自动放行：外审降级、假 FAIL 复跑、限额内重派。只能人工：可行性阻断、数据缺口处置、试跑完成、阻断歧义、切换实验模式、熔断、重派或复审超限、critical 争议、iterate blocked、最终评审、Excel 回改的应用与成本确认。
- 放行记录带选择、用户原话、凭据等级（钩子 / 终端 / 自述）；自述级在看板和报告附录里标注。启动时用 `--policy` 预先声明无人应答时怎么办，默认是停下（部分宿主的提问久未回答会让模型「自行判断」，这正是 r010 的失效模式）。
- 同一（阶段，检查项）连续 3 次 FAIL 即开熔断检查点。G-VF-3 独败是进入 iterate 的设计路径，予以豁免；按此口径回看 12 个案例，只有 r007 的 G-VF-4 连败 6 次会触发。
- 事件流带哈希链，state 记链头，不一致即开篡改检查点。这防的是顺手绕过，不防蓄意伪造。

### 4.4 上下文包与回执（去掉 9 万地板的读、写两半）

**读：任务文件只装这一步需要的内容**

上下文包指内核为某一步拼好的任务文件正文：从原始文书逐字切出的片段，加上这一步的输出合同。表里的「口径卡」是一条假设的精简视图，定义见表后的切片规则。

| 角色 · 步骤 | 任务文件里放什么 | 保真依据 |
|---|---|---|
| extractor、auditor(spec)、三处外审、second_opinion | 不建包，照旧全量 | 盲通道与外审原样保留 |
| planner | 首派全量 spec、矩阵、歧义；重派只追加 FAIL 原文或修订清单 | G-PL、spec 外审 |
| coder（单个 milestone） | 本步要素块全文加「依赖数据」一跳，其余要素各一行索引；主归属假设的口径卡，其余假设各一行；矩阵本步行；plan 的本步段与回测参数；类型模板；`common/` 与直接上游代码的签名 | 内审与外审仍见全部 F/B 要素与全部假设；G-IM-5 |
| auditor(code)（单个 milestone） | 全部 F、B 要素块，本步 D/R/SA，全要素索引；**全部假设的口径卡**；矩阵本步行；`src/` 自读全量 | 8 月方案以「内审持全量假设」作对冲，这里不切；G-CA、code 外审 |
| verifier（单个 milestone） | 本步 R/SA 及其关联要素；主归属假设卡加预期影响；standards 与模板；`src/` 自读全量 | G-VF-3 重算、final verify |
| verifier（final）、auditor(result) | 全部 R/SA/B、全部假设卡、全部图表路径 | G-VF、G-RA |
| diagnoser | 趋势表、已排除假设、上一轮诊断全文、超差指标对应的要素块 | 第 3 轮起恢复全历史；second_opinion 始终全历史 |
| reporter | 机器生成的对比总表、回应汇总、外审台账；假设登记簿全文由内核按模板拼进报告（r009 这一节占报告约 600 行） | G-FN 检成品 |

切片规则：

- 新写一个识别代码围栏的切块器（`mdslice`），不直接用 `check_gates.parse_id_blocks`（`tools/check_gates.py:123`）：它以下一个要素标题为块尾，每章最后一块会吞掉后续章节（三个案例各多吞 6–10KB）。单测断言两者切出的要素 ID 集合一致。矩阵行与 frontmatter 仍复用 `load_matrix_rows`（:206）、`parse_frontmatter`（:94）。
- 本步要素取矩阵 milestone 列与 plan `elements` 的并集。r009 的 SA5–SA7 是 spec_audit 之后补的，只在矩阵里有归属；两者不一致写进包头与事件。
- 引用闭包只取「依赖数据」字段和公式、参数行里的非 R 引用，且只走一跳。传递闭包不可用：r009 的 m5 本步 2 个要素，传递闭包会带进 43 个，等于整份 spec。
- 假设口径卡包含假设内容、参数绑定、影响面、影响指标、状态，以及**最新一条修订记录**。不能按状态分「活跃 / 存档」：revised 的口径正在使用，而且新口径往往只写在修订记录里（r008 的 AS1 标题仍是旧口径）。归属取「影响 milestone」首个括号前的 mN，并上影响指标命中本步要素的；无法归属的进所有包。10 个案例 327 条假设里只有 4 条无归属，不必为此新增门禁，用 `pack lint` 告警即可。
- 包正文必须是原文的逐字节子串（单测断言），包头写明冲突以原文为准。manifest 记片级哈希；若记文件级，verifier 回填一次回看就会让所有 coder 包失效。`done` 时发现消费过的片已变，标「到货即过期」并派差量复核。
- 逃生门只有 `element`、`assumption`、`matrix-row` 三种，不提供按页取原文：那会让 planner、coder 绕过 spec 回原文，spec 的缺口被静默代偿。
- 任务文件、审阅包、事件流、看板加入盲提取外审的禁读清单（`templates/codex_prompts/spec_audit.md`）。外审 CLI 能检索整个工作目录，这些是新的泄漏面。

**写：回执代替回写**

agent 把回填内容写进回执（矩阵行更新、假设回看文本、新增假设条目、参数绑定校正），验证小节写成分片；`flow done` 校验「行属于本步、状态流转合法」后在锁内合并，新假设的编号由内核预留，避免并行撞号。先例是 `tools/assumptions_xlsx.py:346` 的 `apply_param_md_edits`。此后「多个 milestone 的 verifier 不得同批」的限制可以解除；直接改表的旧做法兼容一个版本。

### 4.5 数据体检与缺口处置（含 mock 试跑）

现状是 planner 对着手写目录判断数据可得性，机器不查。改为三道机器检查加一个人工检查点。

**目录体检**（`flow data probe`，setup 与每次 init 时跑，只读元数据）

- 记录数据根下每个文件的字段与类型、行数、日期起止；带证券代码和日期的表再算每年的标的数与交易日数。结果缓存到 `workspace/_registry/data_probe.json`，按文件大小与修改时间失效。
- 由它生成「数据实况表」交给 planner，手写的 `data_catalog.md` 降为说明性文字；两者对不上的地方列为告警。

**需求体检**（plan 阶段内的内核步骤，零 token）

- plan 的 `data_requirements[]` 增加可选的机器可查字段：`files`、`fields`、`period`（含预热窗口）、`freq`、`min_codes`（截面最少标的数）、`core`（是否核心）、`elements`（依赖它的 spec 要素）。非文件来源填一条取数冒烟调用，填不了的记为「未机检」。旧 plan 没有这些字段，只做文件存在性检查。
- 逐条核对：文件在不在、字段齐不齐、区间盖不盖得住、每年标的数有没有塌陷、频率、主键重复、关键字段缺失率、财务类数据有没有披露日列。结论分四种：通过、部分满足（写明缺哪段或哪个字段）、缺失、未机检。
- planner 标了 available 而体检不过：带实测结果退回 planner 改一次；仍不过就进检查点。
- 结果写 `workspace/<id>/data_check.json`。plan 门禁新增两条检查（只对 v3 新建案例生效）：每条数据需求都有体检结论；每个缺口都有处置决定。数据需求后来被改动时体检自动重跑，implement 入口再断言一次。

**缺口处置检查点**（只能人工）

审阅包逐条列出缺什么（附实测证据）、影响哪些要素与指标（顺 spec 的依赖关系传递，宁多勿漏）、是否核心。

| 处置 | 含义 | 之后 |
|---|---|---|
| 补数据 | 你去补 | 暂停；补完 `flow data recheck` |
| 等价替代 | 用本地等价数据。沿用现有 substitute 规则，strict 模式下仍须切到实验模式 | 登记假设，继续 |
| 缩小范围 | 只在有数据的区间或标的上复现 | 登记假设，继续 |
| 先用 mock 试跑 | 用模拟数据先把代码和流水线跑通；这一轮只算试跑，不出结论 | 见下 |
| 砍掉相关要素 | 标为 infeasible（data_missing），其余照做 | 继续 |
| 终止 | 放弃这份研报 | aborted |

启动时可用 `--on-missing ask|mock|stop` 预先声明无人应答时的做法，默认 `ask`，即停下来等。

**mock 只用于试跑**

选了 mock，这个案例整轮就是试跑：

- 照常做的：编码、内审、代码外审。它们不依赖数据取值，真实数据到位后只要代码没变就仍然有效。
- 验证只查三件事：跑得通、产物齐、指标都算得出。然后停在「试跑完成」检查点，不进 iterate、不出 verdict、不写报告。
- 生成：`tools/mockdata.py` 按规格确定性生成（固定随机种子），来源按优先级取：人给的样例文件；借一张结构相近的真实表改键、改日期（保留真实的截面分布与缺失形态，纯随机数据容易算出除零、奇异矩阵或空信号）；都没有才按字段类别随机生成。交易日历与证券代码取本地真实数据，保证与其他表对得上。规格由 planner 起草为 `workspace/<id>/data_mock/spec.yaml`，在检查点给人看。
- 接入：`common/data_loader.py` 新增 `data_path(name)`（先查本案例的覆盖目录，再查数据根）和带列裁剪、日期下推的 `read_table()`，新案例的代码一律经它们取数，不为 mock 写分支。每次运行把读了哪些文件、各自是真实还是 mock、文件指纹、起止时间写成数据清单 `data_manifest.json`。
- 隔离：试跑的结果写到单独的 `output/<id>/results_mock/`（公共函数 `results_dir()` 按是否处于试跑模式返回目录），真实结果目录里只会有真实数据算出来的东西。verify 门禁新增一条检查：真实结果的数据清单里不得出现 mock 文件。
- 「试跑完成」检查点的出口：等真实数据（`flow data recheck` 通过后，结构与 mock 规格一致的只重跑验证，不一致的把相关 milestone 的编码一并标为过期）；改用别的处置，按真实数据走完；终止。
- 不做逐指标的污染传播、真假数据混跑、图表水印。缺的是非核心数据而又想先拿到主体结论，选「砍掉相关要素」或「缩小范围」，数据到了再用 `flow reopen` 补回。

**运行期复核**：verify 时把数据清单里的文件指纹与体检时的对比，数据在两者之间变过就记入证据，用来解释指标漂移。

### 4.6 摘要与机器下沉（吸收 8 月方案）

| 项 | 做法 |
|---|---|
| PDF 撞库 | `init` 算内容哈希并扫已有案例，命中即开检查点提示续跑（r005 / r006 同一 PDF 重跑的教训） |
| 禁读红线与护栏 | 非白名单角色的任务文件里不出现 `report_text.md` / `tables_extracted.md`；扰动产物、运行缓存、ndjson / parquet 不得直接读，写进各角色合同。Claude Code 上再加一道读文件前的钩子，按在途步骤的角色核对禁读清单，命中即拒绝（钩子能否拿到子 agent 身份先实测，拿不到就按在途步骤判断）。Codex 没有对应的拦截点，改为事后核对：采集用量时顺带扫会话记录里的读文件路径，命中记入事件并在看板标出 |

### 4.7 子 agent 内部的轮数纪律

- 回执代替完成报告回流：对主会话只回一行状态。
- 运行类命令的输出重定向到日志，只看尾部与关键行。
- 续派还是新派：改动小且上下文未过阈值才续派，否则带「修复包」（失败证据、diff、相关切片）新派。

### 4.8 计量

三档口径，高档拿不到就回落：

1. **输入侧账本**（必有）：每张工单的任务文件字节数与墙钟，由内核自算。
2. **宿主转述**（仅 Claude Code）：完成通知里的 token 数、工具调用数、耗时，属峰值口径。
3. **宿主记录**（精确）：`flow done` 当场读宿主的会话记录，把未缓存输入、缓存写入、缓存读取、输出四项分开记。Claude Code 的子 agent 转录逐条消息带这四项，同名元数据文件带派发描述；Codex 的会话记录带累计 token 计数（分叉式派发会继承父计数，要扣基数）。工单规定连接键：Claude Code 的派发描述、Codex 的任务名都等于 `step_id`。两种记录格式都没有公开承诺，Claude Code 的还会被定期清理，所以只当增强、不当依赖。

主会话开销读得到记录就取精确值，否则以内核调用次数、输出字节数、轮询次数作代理。`flow cost <id>` 按阶段、角色、步骤汇总。

外审进程和每次运行同样入账：外审的 token、耗时、读文件次数、有没有分出子代理，取自外审引擎自己的会话记录；`main.py` 每次运行的起止时间取自数据清单。

### 4.11 外审引擎

r010 暴露的五个问题各有对策，都落在 `tools/external_review.py` 与内核的外审模块里，三个审查点共用。

| 问题（r010 实测） | 对策 |
|---|---|
| 输入只给路径，审查方靠约 360 次命令分段读 | 内核预先拼好输入包随提示词送入：所需文件带行号的全文（方便直接引用 `文件:行号`）、R 类数值字面量在 `src/` 的命中清单、`common/` 签名。按外审引擎的上下文上限设预算，超出部分按优先级改为只列路径和行数。审查方仍有整个目录的只读权限，要多看随时可以读 |
| 推理强度跟着全局配置走，r010 当时是 ultra | 命令里显式指定：首轮默认 high，复审 medium，可在 `.reproduce.json` 里按审查点调整 |
| 审查方自己再分出 2–3 个子代理 | 调用时关闭多代理特性（`codex exec --disable multi_agent`，实现时验证）；事后从会话记录核对子会话数为零。Claude 作外审引擎时工具集里本来就没有子代理 |
| 复审等于重审 | 第二轮起只给差量包：上一轮的意见与回应、上一轮输入包与当前文件的差异。只核对每条意见是否闭环、改动处有没有引入新问题。改动面过大（默认超过三成行数）或人要求时才整体重审 |
| 超时即作废，再原样重试 | 后台执行，时限放宽到 30 分钟（可配）。超时后降一档推理强度、原输入重试一次，仍超时再走降级链。不缩减输入：现行执行卡的「缩减输入重试」没有定义怎么缩（`stages/spec_audit.md:53`），盲提取尤其不该缩 |

盲提取改为两次调用：第一次的输入包里只有原文与表格，第二次才给 spec 和第一次的产出；两次的输出按现有格式拼成一个文件，门禁解析不变。现在两个阶段写在同一份提示词里，只靠审查方自觉；拆开后可以从会话记录核对第一次调用没有读过 spec。

输出用 `--output-last-message` 落盘，JSON 部分用 `--output-schema` 约束，减少解析失败。外审的用量与耗时记入事件流（见 4.8）。

### 5.3 失效标注与重开

- 每步派发时，内核把它消费了哪些片、各片的哈希写成 manifest（`workspace/<id>/flow/manifests/`），依赖边由此而来。过期判定：已完成步骤消费过的片，当前哈希与 manifest 不同。内核自己的写入记事件，不算外部改动。

| 变更 | 过期范围 | 重入点 |
|---|---|---|
| spec 要素块 | 消费过它的步骤及其后链 | plan，或相关 milestone 的编码 |
| plan 的某个 milestone 段、回测参数 | 该 milestone 的编码、内审、验证，及依赖它的 milestone | 该 milestone 的编码 |

| `comparison.json` | 结果审计、报告 | result_audit |

- implement 内按 milestone 子步骤续跑；会话中断后 `continue` 从步骤级恢复。

### 7.2 第四期：多篇引用 + 知识库

**多篇引用**

- 一个案例可挂多份资料：`state.ext.sources[]` 区分主文档、同册多篇（如 r009 合订版）、参考文献；`flow init --ref <文件>` 与 `add-source` 追加。页码引用扩展为 `S2:p5`，主文档仍写 `p5`，旧案例不受影响。
- extractor 多产一份引用台账 `spec/references.md`：被引对象、缺的是什么（关联要素 ID）、关键度、解决状态。
- 解决顺序：用户已提供 → 知识库检索 → 本地案例库（该研报是否已复现过）→ 可选联网 → 登记为假设。关键且无解的，开检查点向人要原文。
- 被引研报已复现过的，记 `depends_on` 血缘，直接复用其 spec 要素与代码。

**知识库建议：分三层，依赖由低到高**

1. **本地案例库（所有客户默认具备，零依赖）**：`workspace/_registry/` 下的 `cases.jsonl`（每案一行：PDF 哈希、标题、机构、类型、结论、评级、关键指标、可复用资产、代码入口）和 `lessons.jsonl`（诊断归因与外审确认的问题，带类型 / 数据源 / 坑类标签）。它同时解决三件事：同 PDF 撞库提示、planner 分诊时取同类经验、被引研报的复用。其中 PDF 哈希索引本轮就做。
2. **quant_wiki 专用适配（作者自用首选）**：它已有 kb-mcp 检索、来源卡与实验卡模板、明确的写入边界（agent 只能写 `experiments/` 与 `inbox/`），且 `report-deep-read` 技能已经会生成「复现开发计划」实验卡。闭环为：研报入库 → 深读 → `/reproduce`（读来源卡深读章节作提示，被引研报先在库内检索）→ accept 后把结论回写同一张实验卡（状态、结果、失败原因、结论、下一步，引用用 `[^src-id#page-x]` 与 `[^backtest:路径]`），因子与策略草稿进 `inbox/` 等人工晋升。
3. **通用 Markdown 写出（客户自己的笔记库）**：accept 后把「复现卡」（frontmatter + 双链）写到配置的目录，模板可替换。覆盖「因子挖掘结果」库和任何客户的 Obsidian 库。这一层很薄，随第 2 层顺手做。

三层共用一份规范化的导出物 `workspace/<id>/export/case_card.json`，各写出器只做格式转换。本体写出归第五期。

### 7.3 第五期：本体与量研桌面（可选适配，默认关闭）

## 十一、不做的事与风险

**本轮不做**

- 不改任何现有门禁检查项的判定语义（只新增数据类与一致性类检查项），不改机器解析的文书格式（数据需求只加可选字段），不把 `spec.md` 迁成结构化记录。
- 不裁刻意冗余：外审双通道与盲提取全文、auditor(code) 与 verifier 对 `src/` 的全量读、内审持全部假设、扰动测试、逐张图表目检、extract 与 plan 的隔离。
- 不新增「影响 milestone 非空」门禁（r009 的 AS44 会被判败），用告警代替。
- 不做去掉编排会话的脚本直驱；等桌面宿主那一期再评估。
- 不单列公共引擎提速批次。实测单次完整运行 r010 约 5 秒（coder 已自己做了列裁剪与日期下推）、r008 约 12 秒、r009 约 22 分钟、r007 约 15 分钟；慢的两例，一个基本不经过公共引擎（`src/` 里 63 处直接读文件，另有接口取数），一个慢在模型训练。本轮只加 `read_table()` 并把运行耗时入账，下一份案例跑完按数据再定。
- mock 不做逐指标的污染传播与真假数据混跑。
- 数据库、API、MCP 的数据适配与快照，引用台账、知识库写出、本体适配本轮只留扩展点。

**风险与对策**

| 风险 | 对策 |
|---|---|
| 步骤表与原执行卡行为漂移 | 分批迁移，未入码的阶段走原执行卡；批次 A 的门禁输出比对、回放测试对齐历史门禁结论；保留 v2.12.0 标签可回退 |
| 切片漏给上下文，审计变薄 | 一跳闭包加索引、逃生门、全量通道原样保留；按角色逐个灰度；以第十节第 5 项的保真指标把关 |
| 任务文件与审阅包成为盲提取的泄漏面 | 加入外审禁读清单；盲通道不建包 |
| 编排会话伪造「人工放行」 | 等待态内核只返回 halt；流转守卫；放行记录带原话与凭据等级并在报告中列示；宿主支持时用钩子或终端短码硬化 |
| 回执是 agent 自述 | 只用于路由与回填，放行只认门禁 |
| mock 数字混进结论 | 用了 mock 整轮只算试跑，不出 verdict、不写报告；试跑结果写在单独的目录；数据清单记录每个文件的来源，门禁拦截 |
| 步骤表漏判，案例被内核卡死 | 工具层与调度层分开；任何阶段可用 `flow pin` 退回执行卡驱动；步骤表是一张声明式的表，回放测试覆盖 6 个历史案例 |
| 外审降低推理强度后查得不够深 | 首轮默认 high（与当前全局配置一致），只有复审降到 medium；按审查点可调；外审重放时比较发现数与严重度 |
| 输入包超出外审引擎的上下文 | 按引擎上限设预算，超出部分只列路径；包大小记入事件 |
| 宿主会话记录格式无公开承诺 | 用量三档回落，输入侧账本始终可用 |
| 后台外审进程在某些宿主沙箱里活不过命令返回 | 适配卡声明各宿主的后台原语；不可用时退回前台分段等待 |
| state 与事件两文件非原子 | 先写事件后写 state，以 state 为准，`done` 幂等 |
| 在跑案例迁移出错 | 迁移幂等且留 `state.v1.json`；12 个真实 state 进迁移测试 |

**与上文不一致的地方**

1. 迁移改为显式命令 `flow migrate`，没有做成「`load_state` 在内存里升级，首次写盘时落地」（4.9）。旧版本工具对 state 做严格校验，读不了 v2 文件；同一个工作区可能还被旧版本的插件副本使用，悄悄升级会让它报错。新建案例仍默认 v1，等内核接管 init（批次 C）再改默认值。
2. 案例锁、事件追加和哈希链放在 `tools/state.py`，因为它是状态的唯一写入口；`tools/flowlib/events.py` 只负责读时间线和生成描述（第九节原写由它负责追加、哈希链与案例锁）。
3. 工具层命令里的 `flow gate`、`flow get`、`flow pin` 本批没有提供。`next` 已经会读 `flow.pinned`，但本批所有阶段本来就由执行卡推进，钉与不钉没有区别；迁移时也不替案例预先钉阶段，改为在内核接管某个阶段时按案例当时的状态判断。
4. 口径卡在 4.4 所列字段之外还带「影响 milestone」；登记簿里认不出的字段原样带入，没有「假设内容」字段的条目整块带入。原因是真实登记簿里有把口径写在非标准字段里的条目，按白名单裁会丢内容。
5. coder 包里的 `common/` 签名按报告类型裁剪：基础三个模块、该类型的引擎、类型模板点名的模块、上游代码引用的模块。不裁时每个包都带着全部引擎的签名（28–39KB），coder 包的中位比例是 50%，裁后降到 37%。
6. 旧案例没有 4.8 所说的连接键，用量按估计规则归属：取案例第一条到最后一条状态事件之间（前后各一小时）、工作目录相同、且提到本案例的行数比提到其他任何案例都多的会话，只算这段时间内的调用，子代理跟随父会话。试过按状态事件聚出的活动时段切片，会把专属主会话少算两成（r007 的主会话为 1.71 亿对 2.13 亿），没有采用。
7. 数据目录体检除元数据外还读代码列与日期列来算每年的标的数，所以首次全量要一分半钟（第二节说的 0.1 秒是只读 118 个顶层文件的元数据）；`--no-yearly` 可以只读元数据。
8. 看板上「等了多久」从进入当前状态的那条事件算起，不取 `updated_at`，否则迁移这类维护动作会把等待时间归零。
9. 4.9 预计迁移后 `state.json` 从 30–49KB 降到几 KB，实测没有做到：10 个走完多个阶段的案例迁移后是 22–29KB（迁移前 23–49KB）。留在 state 里的 50 条事件约占 10–13KB，各阶段最新一条门禁（带逐项说明）约占 7–10KB。要再降只能少留事件或去掉门禁的逐项说明，本批没有动，留待验收时定。

**留给后续批次**

`flow init / done / fail / adhoc / decide` 等推进与人工命令、状态流转守卫、检查点与审阅包、任务文件的投喂与回执、数据需求体检与缺口处置，均按第六节的批次安排。

**与上文不一致的地方**

闸门与检查点

1. 方案 4.3 列的「切换实验模式」「Excel 回改的应用与成本确认」没有做成独立检查点。前者并入可行性阻断的 `experimental` 选项与数据缺口的「等价替代」；后者并入 `flow revise --from-excel --dry-run`（先给出影响面与重跑范围，人确认后去掉 `--dry-run` 并带原话执行）。
2. `--on-missing` 三个取值里只有 `mock` 改变内核行为：数据缺口与模拟数据规格两个检查点按「先试跑」自动放行，凭据记为「策略」级。`ask` 与 `stop` 在内核里都是停下等人，差别只在编排会话是否追问。
3. 同宿主替身也交不出结论时，这一轮记为跳过并继续，不开检查点（方案只写到「走降级链」）。外审任务连提示词都没准备出来时同样记为跳过，不派替身。
4. 假 FAIL 分诊里「验证期间确有别的 milestone 在编码」按事件流里的先后顺序判断，不比墙钟时间。
5. hard 难度的「milestone 完成」检查点等到该 milestone 的内审有结论之后才开，否则审阅包里没有内审结论。
6. 评审类检查点多了一个选项「已经直接改了文件」，与「修改后继续」分开：前者由内核重新核对，后者把人说的话交给属主角色去改。
7. 禁读护栏除禁读清单外，还拦截对 `state.json`、事件流和「人在场」记录的写入。钩子靠子 agent 第一次读自己的任务文件来认定它在做哪一步；对上级目录做检索这类绕法钩子拦不住，只由事后核对覆盖。

上下文包、回执与失效

8. 「到货即过期」只留痕并在点收输出里提示，不自动派差量复核；要不要重做，由人看过期报告后决定。
9. 过期判定用「稳定指纹」：矩阵行只算 plan 定下的列，假设卡不算参数绑定、状态、回看这几个由内核合并回执时改写的字段，否则每合并一次回执就会让别的步骤过期。过期报告另外区分「只是对照用的上下文变了」和「自己负责的内容变了」，建议的重开起点只取后者。
10. 角色合同没有整体改写成「只按任务文件执行」，而是在原合同前面加一节「两种派发方式」：内核派发按任务文件，执行卡派发按原合同。旧案例和被退回执行卡的阶段还要用原合同。
11. 任务文件里「不要直接改矩阵和假设登记簿」这句话只对回执里带这两类回填的角色出现；计划者、提取者本来就是这两份文件的作者。

数据体检与 mock

12. 「砍掉相关要素」的处置按数据需求的名称沿用：planner 重写 plan 后，名称没变的需求不再重新问一遍。
13. 人改主意换一种处置方式时，原处置清空但保留一条痕迹（`cleared_disposition`）。
14. 取数冒烟命令（plan 里的 `probe` 字段）默认不执行，记为未机检；`flow data check --smoke` 才执行。

预检、报告与迭代

15. 预检的三处取舍保持默认（都是 `precheck.py` 顶部的开关）：来源要素没对上、但指标编号或名称以要素编号开头的条目，也算该要素有条目，另出一条提示（r008 的来源要素写的是图表编号）；不一致的计数或手抄值，如果文书后文已有一致的写法，按旧数残留只提示不拦截；文书写的达标数恰好等于 `comparison.json` 自述的计数、却与重算不符时照样拦截（r010 属于这种）。有提示而没有拦截项时，给文书属主一轮不计数的清理机会。
16. 报告写完后多了一步一致性核对（方案只在写报告之前核）：机器结果以外的问题出在哪份文书就退给谁，报告里手写的计数或数值对不上就退给 reporter。达标计数那一行放在对比总表的机器生成块里。
17. 样本外分析与结果审计并行时，内核记下样本外开跑那一刻的代码与对比表指纹；结果审计的修复改了其中任何一个，样本外作废重做（方案没有写到这种情况）。
18. 迭代摘要按方案先灰度：默认与全部历史一起给诊断者（`flow.iterate_digest` 为 `shadow`），改为 `on` 后第 2 轮只给摘要与上一轮诊断，第 3 轮起仍给全部历史。

外审

19. Codex 的多代理用 `-c features.multi_agent=false`、`-c features.multi_agent_v2=false` 关闭，没有用 `--disable`：特性改名时，写一个不认识的配置键不会报错，`--disable` 一个不认识的特性名会让整条命令失败。
20. 输入包默认预算从方案设想的「按引擎上限」落到 codex 320KB、claude 200KB（最初实现为 600 / 500）。依据是真实重放的实测：288KB 的输入包对应约 15.6 万 token 的上下文峰值，大约 2 字节一个 token；超出窗口整次调用作废，而放不进包的文件只是改为列路径、审查方按需自己读，所以宁小勿大。窗口更大的引擎在 `.reproduce.json` 里调高，可按审查点单独设。「输入超出上下文」单列为一种失败原因，不重试，并提示调小预算。
21. 进程失败后的那次重试去掉输出约束，防止失败正是约束被引擎拒绝；结论解析不出来则带着约束重试。
22. 盲提取的第一次调用读过 spec 时只留痕（事件流、台账、点收提示），不作废这一轮。
23. 已有的规范文件不是本模块生成的（旧案例手写的汇总）时，先原样收编为第 0 轮；目录里编号更大的旧轮次挪到 `audit/external/_superseded/`。
24. 后台进程的工作目录是插件根，工作区根经环境变量传入，免得工作区里另有一份同名 `tools/` 时跑到别的代码上。
